# SolArch — Security Specification & Threat Model

---

## 1. Security posture

SolArch защищает цифровой контент practical DRM-моделью.

Цель:

- не хранить decryption key в `.slr`;
- отделить payment от license;
- привязать activation к device key;
- не выдавать raw files через обычный Viewer UI;
- усложнить несанкционированное распространение;
- добавить buyer-specific traceability.

Не обещать абсолютную защиту после отображения контента.

---

## 2. Trust boundaries

### Browser

Untrusted.

Нельзя доверять:

- price;
- ownership;
- payment success;
- analytics counters;
- entitlement decisions.

### Viewer

Partially trusted.

Viewer работает на устройстве пользователя и теоретически может быть модифицирован.

Поэтому:

- payment verification серверный;
- server-signed license;
- content key выдаётся после server authorization;
- device private key stays local.

### Backend

Trusted decision boundary.

Requires:

- secret management;
- auth;
- authorization;
- logging redaction;
- validation;
- rate limiting;
- transaction verification.

### Object Storage

Не считать plaintext-security boundary для protected buyer content.

Generated `.slr` остаётся encrypted.

---

## 3. Critical secrets

Нельзя логировать/коммитить:

```text
SolArch fee payer private key
license signing private key
content keys
device private keys
creator private keys
buyer private keys
storage credentials
database passwords
JWT/session secrets
```

Use `.env.example` without real values.

---

## 4. `.slr` security

Mandatory:

- no plaintext content key;
- authenticated encryption;
- unique nonces according to algorithm requirements;
- integrity verification;
- signed container metadata;
- version validation;
- corrupted chunk rejection;
- path normalization;
- size/file-count limits.

---

## 5. Upload security

Protect against:

```text
path traversal
zip slip
zip bombs
excessive nesting
duplicate normalized paths
malformed archive parser input
unexpected executable files
oversized uploads
```

MVP should reject executable content.

Source upload never becomes public buyer download.

---

## 6. Payment threats

### Fake frontend success

Mitigation: backend chain verification.

### Wrong recipient

Mitigation: verify creator and platform recipients.

### Wrong amount

Mitigation: verify both split amounts.

### Wrong token

Mitigation: configured USDC mint only.

### Replay

Mitigation:

```text
transaction_signature UNIQUE
idempotency
payment intent binding
```

### Modified price

Mitigation:

```text
immutable server-side price
payment intent generated by backend
```

### Fee payer key theft

Mitigation:

- server-only secret;
- limited hot-wallet SOL balance;
- monitoring;
- rotation/incident process.

---

## 7. Licensing threats

### Copy `.slr` to second device

Mitigation: device-bound activation and `max_devices = 1`.

### Forge local license

Mitigation: server signature validation.

### Copy device license file

Mitigation: license bound to device public key and wrapped content key.

### Extract content key from memory

Cannot be absolutely prevented.

Mitigation:

- short plaintext lifetime;
- chunked decryption;
- avoid disk plaintext;
- Rust core;
- best-effort hardening.

---

## 8. Device key

Requirements:

```text
device_private_key stays on device
stored through OS secure storage
device_public_key sent to backend
```

Never derive identity from MAC address.

---

## 9. Viewer security

Protected content should:

- render internally;
- avoid persistent plaintext temporary files;
- avoid external open;
- avoid standard export;
- use watermark.

Do not claim that screenshots/screenscreen recording are impossible.

---

## 10. Watermark

Visible watermark includes traceability fields such as:

```text
buyer wallet short
license id short
archive id short
```

Watermark is deterrence and attribution, not cryptographic access control.

---

## 11. Marketplace security

Public endpoints reveal only public fields.

Never expose:

```text
original source storage URL
content key
private manifest
chunk map
internal object storage key
other buyers' device/license data
creator secrets
```

Unpublished/blocked archive must not be publicly downloadable.

---

## 12. Authorization

Every creator-only action performs backend ownership check:

```text
authenticated_user owns archive
```

Frontend route protection is insufficient.

Admin override is explicit and audited where implemented.

---

## 13. Analytics abuse

Public views/downloads can be manipulated.

MVP mitigation:

- server-side events;
- anonymous session ID;
- deduplication window;
- rate limits;
- do not trust client-supplied totals.

`paid_unlocks` is blockchain-verified and strongest metric.

---

## 14. Logging

Logs may contain:

```text
request_id
archive_id
payment_intent_id
transaction signature when operationally necessary
error code
timing
```

Logs must not contain:

```text
content key
private keys
raw license secret material
decrypted file content
auth tokens
```

---

## 15. Threat matrix

| Threat | Severity | MVP mitigation |
|---|---:|---|
| Copy `.slr` | Medium | Device license |
| Fake payment UI | High | Backend verification |
| Wrong recipient/amount | High | Full tx validation |
| Payment replay | High | Unique signature/idempotency |
| Content key in container | Critical | Forbidden |
| Storage leak | High | Encrypted `.slr`, key separate |
| Fee payer compromise | Critical | Secret isolation + limited funds |
| License forgery | High | Server signatures |
| Viewer reverse engineering | High | Practical hardening only |
| Screen recording | High | Watermark / no absolute promise |
| Path traversal | High | Safe extraction |
| Zip bomb | High | Limits |
| Public source-file leak | Critical | Controlled download only |

---

## 16. Security Definition of Done

Before demo/merge:

- no real secrets in repository;
- `.env.example` exists;
- wrong amount test fails;
- wrong recipient test fails;
- wrong mint test fails;
- replay test fails safely;
- corrupted `.slr` fails closed;
- forged license fails;
- Device B limit test passes;
- source ZIP cannot be fetched publicly;
- logs reviewed for secret leakage.
